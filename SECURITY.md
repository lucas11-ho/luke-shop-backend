# Security — Luke Shop Backend v0.5.0

Existing session, RBAC, tenant isolation, inventory transaction, checkout idempotency, payment, delivery, and promotion controls remain in force.

## Luke CS / AI gateway

- No direct Shop database access is exposed to Luke CS or AI.
- Integration credentials are hashed with the server-side credential pepper.
- Integration clients explicitly declare `STAFF` or `AI` usage mode.
- AI credentials cannot use legacy customer-ID commerce routes.
- Long-lived credentials cannot call the AI tool gateway; the gateway requires a short-lived signed service JWT.
- Customer support contexts use a separate JWT audience and bind tenant, customer, live customer session, store, and allowed read tools.
- Production uses distinct `CS_CONTEXT_SIGNING_SECRET` and `CS_SERVICE_SIGNING_SECRET` values.
- Revoked/expired customer sessions or contexts immediately fail even when a JWT has not yet reached its cryptographic expiry.
- Every tool request requires a fresh timestamp and one-time nonce; only the nonce SHA-256 hash is stored.
- Context tool names are constrained to the v0.5 read-only allowlist in both application policy and migration schema.
- Service scope, context allowlist, tenant general policy, and AI policy are all checked before executing a tool.
- Order/payment/delivery reads are tenant + customer + store bound.
- Tool responses omit private storage keys, shipping addresses, customer email, provider/customer payment references, failure internals, and tracking URLs.
- Tool audit rows do not copy full result payloads.
- Per-client tenant tool limits are applied in addition to Fastify endpoint rate limiting.

## Secret handling

Never commit `.env` or service credentials. In production configure separate, high-entropy values for `JWT_ACCESS_SECRET`, `SERVICE_CREDENTIAL_PEPPER`, `CS_CONTEXT_SIGNING_SECRET`, and `CS_SERVICE_SIGNING_SECRET`.

## Deliberately unavailable in v0.5.0

AI/CS cannot cancel orders, issue refunds, change addresses, change payment/delivery details, mutate customers, run arbitrary SQL, or call arbitrary backend endpoints through the tool gateway.

## v0.6.0 Merchant Staff & RBAC controls

- Merchant staff/role/session queries are tenant scoped from authenticated context.
- Password hashes and refresh-token hashes are never returned by staff APIs.
- Only OWNER can assign/manage OWNER membership.
- Custom-role grants are constrained to permissions the acting merchant already possesses (OWNER bypasses as tenant super-admin).
- System OWNER role cannot be changed or deleted.
- Suspend/disable, password reset, force logout, and session revoke invalidate sessions in PostgreSQL.
- Sensitive operations write tenant audit events.

## Platform v0.7.0
Platform access tokens use a dedicated audience and separate session table. Tenant clients cannot use merchant credentials to reach platform-owner APIs. Storefront experience accepts only normalized allowlisted configuration; arbitrary scripts/HTML are not supported.


## Media Asset Library (v0.8.0)

Uploads are tenant/store scoped and require merchant catalog permissions. Storage keys are generated by the backend. SVG and HTML uploads are not accepted. Supported image/video uploads are MIME allowlisted and checked against basic file signatures before storage. Public and private assets remain distinct. Production deployments must configure `ASSET_PUBLIC_BASE_URL`.
